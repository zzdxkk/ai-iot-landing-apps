# AI 应用与物联网平台：10 个小工程

10 个互相独立的小工程，拼起来是一条完整链路：设备接入与边缘判断在下面，AI 应用在上面。

**AI 应用侧**

- 01 知识库问答：文档切块 → 检索 → 带出处的回答
- 02 工作流编排：工具调用循环 + DAG 依赖调度
- 03 效果评测：多指标打分、A/B 回归、Markdown 报告
- 04 内容管线：模板批量生成 → 合规审核 → 导出
- 05 客服工单：意图识别、槽位抽取、知识匹配、转人工

**物联网侧**

- 06 设备接入：物模型校验、设备影子、规则引擎告警
- 07 Modbus 网关：CRC16、RTU/TCP 帧解析、寄存器换算
- 08 水务边缘监测：EWMA 边缘异常检测、低功耗占空比
- 09 OTA 升级：分包、逐包校验、断点续传、灰度
- 10 预测性维护：振动特征、健康评分、剩余寿命估算

## 每个工程解决什么问题

| # | 工程 | 解决的问题 | 入口 |
| --- | --- | --- | --- |
| 01 | RAG 知识库问答 | 制度文档散在各处，答案还得能核对出处 | `python3 src/rag.py` |
| 02 | 多智能体工作流 | 多步任务要按依赖顺序跑、失败要能重试 | `python3 src/agent.py`、`python3 src/workflow.py` |
| 03 | 大模型应用评测 | 改了提示词或模型，说不清到底变好还是变差 | `python3 src/evaluator.py` |
| 04 | AIGC 内容管线 | 批量生成时提示词散乱、质量与合规不可控 | `python3 src/pipeline.py` |
| 05 | AI 客服工单 | 重复咨询占人力，工单字段靠手填 | `python3 src/service.py` |
| 06 | MQTT 设备接入 | 设备上报要先校验、留最新状态、异常要立刻告警 | `python3 src/hub.py` |
| 07 | Modbus 工业网关 | 现场设备讲 Modbus，平台讲 MQTT/HTTP，中间要翻译 | `python3 src/modbus.py` |
| 08 | 水务边缘监测 | 电池供电设备不能一直上报，得在端上判断哪些数据值得发 | `python3 src/monitor.py` |
| 09 | OTA 升级服务 | 野外设备升级怕半包、坏包、断线，还得灰度 | `python3 src/ota.py` |
| 10 | 预测性维护 | 设备突发停机代价高，想从"事后修"提前到"提前换" | `python3 src/phm.py` |

每个目录都有自己的 README，写清做法、验证结果和边界。

## 一条命令验证

```bash
./run_all.sh
```

它会逐个跑演示入口、单元测试，最后单独对 01 的 HTTP 接口做一次冒烟请求；任何一处失败都以非 0 退出。当前结果：**10 个演示入口正常，47 项单元测试通过**。

## 设计上的取舍

- **零第三方依赖**：全部用 Python 标准库，`python3` 直接跑，不需要装环境。
- **外部系统用模拟代替**：模型、MQTT broker、传感器、串口都以本地实现替身，把链路和边界条件做出来，而不是靠调用外部服务。
- **可替换的接口**：向量化、生成、存储都留了替换点（换成真实模型或 broker 只改一个类/函数）。
- **每个工程都有边界说明**：做到哪一层、没做什么，写在各自 README 的最后一节。

## 边界

这 10 个工程是**可运行、可测试的练习工程**，不是生产系统：没有接真实模型与硬件，也没有做权限、持久化、并发与可观测性。它们的价值在于把协议细节和设计取舍落到实处，能跑、能改、能被追问。
